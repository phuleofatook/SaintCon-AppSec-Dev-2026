# SaintCon AppSec Developer Track — Code Review Challenge Corpus
This is a sample corpus generated by an AI assistant.  It is not a final corpus, just a starting point.

## Purpose

This document is the implementation reference for the SaintCon AppSec Developer Track code-review booth.

The attendee sees only:

1. Tracking ticket
2. Proposed PR
3. **APPROVE / DENY**

The attendee does **not** see the review metadata or answer rationale.

The corpus is intentionally broader than vulnerability detection. The core skill is deciding whether a proposed change should ship.

The conference theme is **SAINTCON Spaceways: Flight 26**, but the technical scenarios are theme-neutral. The thematic dressing below is presentation-only and must not alter the technical premise, decision, difficulty, or required reasoning.

## CR-01 — Add Greeting Function

**Ticket title:** Add Greeting Function

**Ticket requirements:**

> Add a small greeting function for the application's landing page.
>
> Requirements:
> - Accept a destination name.
> - Return `Hello, <destination>!`.
> - Do not modify the destination text.

**PR title:** Add `greet()` helper

**PR description:**

> Adds a small helper used by the landing page to generate the greeting.

**Minimal existing context:**

```text
LandingPage
    -> greet(destination)
    -> display returned string
```

**Proposed change:**

```text
function greet(destination) {
    return "Hello, " + destination + "!";
}
```

**Correct decision:** APPROVE

**Category:** APPROVE — Ordinary safe change

**Difficulty:** EASY

**Security concept:** None

**What a good reviewer should notice:** The implementation directly satisfies the ticket.

**Why:** No meaningful correctness or security problem is present in the supplied context.

**Common incorrect reasoning:** Rejecting because arbitrary HTML could theoretically be passed as a destination, without evidence that the result is rendered as HTML.

**Additional investigation:** Confirm rendering context if this were production review.

**Language-independent:** Yes.

**Larger application knowledge:** No.

**AI-review characteristics:** Baseline scenario. AI may invent an XSS concern from string concatenation alone.

**On-ramp:** YES

**Judgment-based:** No.

**Spaceways dressing:** “Greet Our Destination” / `Hello, Mars!`

# HARD / JUDGMENT Scenarios

## Judgment Design Rule

A pre-existing vulnerability is **not automatically an APPROVE judgment scenario**.

Use this test:

> Could the developer reasonably fix the vulnerability with a small, local change while already modifying this code?

If **yes**, it should generally be **DENY**, even if the vulnerability predates the PR.

Examples:

| Existing issue | Judgment? | Reason |
|---|---|---|
| SQL concatenation → parameterized query | No; usually DENY | Small local fix |
| Missing authorization check → add check | No; usually DENY | Small local fix |
| Missing HTML encoding → encode output | No; usually DENY | Small local fix |
| User IDs represented as strings throughout system | Yes | May require API/schema migration |
| Enumeration-resistant identifiers require redesign | Yes | Architectural change |
| Authorization model spans multiple services | Yes | System design change |
| Legacy serialization format has many consumers | Yes | Compatibility/migration |
| Vulnerable dependency is deeply embedded | Yes | Broad compatibility impact |
| Database schema redesign required | Yes | Beyond normal PR scope |

The goal is **not** to teach “leave pre-existing vulnerabilities alone.” The goal is to teach:

> **Needs fixing ≠ must be fixed in this PR.**

# Supply-Chain Scenarios

Supply-chain issues should be represented primarily as **HARD/JUDGMENT scenarios**, not as CVE trivia.

The reviewer should not need external vulnerability databases.

The useful question is:

> Does this PR unexpectedly change what code, build process, or artifact source the project is trusting?

These scenarios should generally involve a small multi-file PR:

```text
package/dependency manifest
lockfile
application/build configuration
possibly a small source change
```

The changed application code should often be harmless. The security-relevant behavior can live entirely in the dependency/build changes.

## Recommended Supply-Chain Scenario S-01 — Unexpected Dependency Behavior

**Ticket:** Add thumbnail generation.

**PR:** Adds image-processing dependency.

**Context:** The dependency's normal installation now executes a remote download script to retrieve a native binary.

**Decision:** DENY or judgment depending on supplied repository policy.

**Review skill:** Understand build-time trust boundaries.

**Why this works:** No CVE lookup is required. The reviewer notices that a normal library addition introduces execution of remotely retrieved code during installation.

**Difficulty:** HARD.

**Judgment:** Prefer YES if the repository has an established internal artifact verification process that might make the behavior acceptable.

---

## Recommended Supply-Chain Scenario S-02 — Unexpected Lockfile Change

**Ticket:** Update image library to support a new image format.

**PR:** Changes one direct dependency, but the lockfile contains hundreds of unrelated dependency changes.

**Decision:** DENY pending investigation.

**Review skill:** Scope analysis and dependency integrity.

**Why this works:** The reviewer doesn't need to know whether any dependency is vulnerable. The PR's dependency impact is unexpectedly broad.

**Difficulty:** HARD.

**Judgment:** YES if there is a plausible explanation, such as an intentional major dependency-tree migration.

---

## Recommended Supply-Chain Scenario S-03 — Dependency Source Change

**Ticket:** Use the organization's shared logging package.

**PR:** Changes package resolution so the dependency can come from a public registry instead of the organization's private registry.

**Decision:** DENY.

**Review skill:** Dependency provenance and trust boundaries.

**Difficulty:** HARD.

**Judgment:** Potentially YES if the repository explicitly permits public fallback resolution and integrity controls are established.


The attack should emerge from an ordinary product change.

The core review question is:

> What data is untrusted, how does it enter the model context, and what authority does the model's output have?

**Difficulty:** MEDIUM.

**AI comparison:** AI may overreact to the prompt injection possibility and reject a change whose output is safely contained.

# Final Corpus Audit

## Balance

The corpus intentionally contains a healthy mix of:

- ordinary APPROVE;
- security-improvement APPROVE;
- security-problem DENY;
- non-security DENY;
- contextual judgment.

The goal is that **security-sensitive code is not synonymous with DENY**.

## Security concepts

The corpus avoids becoming a one-example-per-OWASP list. Concepts include:

- SQL injection
- XSS
- broken access control
- IDOR
- multi-tenant authorization
- authentication/session security
- sensitive data exposure
- file handling
- SSRF
- unsafe deserialization
- command injection
- TLS validation
- least privilege
- brute-force protection
- auditability
- supply-chain integrity
- prompt injection
- AI output authority

SQL injection and XSS appear more than once because they support different review lessons, but the corpus should not be expanded by simply adding more examples of those vulnerabilities.

## Non-security defects

CR-34–36 intentionally make the attendee review ordinary software correctness:

- explicit ticket requirement violation;
- null/error handling;
- ordering regression.

Consider adding additional non-security scenarios in later versions. They are valuable because attendees may initially assume a security booth means “find a vulnerability.”

## Judgment scenarios

The key rule is:

> A pre-existing vulnerability is not automatically a reason to approve a PR.

If the vulnerability is a **small local fix** and the reviewer is already modifying that code, DENY is usually more appropriate.

Examples that generally should **not** be APPROVE judgment scenarios:

- SQL concatenation that can be parameterized in two lines;
- missing authorization check that can be added locally;
- missing HTML encoding;
- obvious hard-coded secret that can be moved locally.

Good APPROVE judgment scenarios involve problems whose remediation reasonably requires:

- API migration;
- database/schema migration;
- identifier-model redesign;
- authorization architecture changes;
- cross-service coordination;
- compatibility migrations;
- broad dependency upgrades;
- major session/authentication redesign.

The intended lesson is:

> **Needs fixing does not necessarily mean “fix it in this PR.”**

A reviewer should be able to recommend:

> APPROVE this PR + create a separate remediation item.

That is different from ignoring the vulnerability.

## Supply chain

Supply-chain scenarios should not depend on:

- knowing a particular CVE;
- recognizing a famous malicious package;
- external Internet research;
- suspicious package names.

Instead, test:

- dependency provenance;
- unexpected dependency-tree changes;
- unexpected build/install behavior;
- lockfile integrity;
- package-source changes;
- executable artifacts;
- trust boundaries.

These are naturally HARD because they may require reviewing several changed files.

## Prompt injection

Prompt-injection scenarios should not reveal themselves through:

- `AGENT:`;
- `IGNORE PREVIOUS INSTRUCTIONS`;
- comments announcing the attack;
- malicious-looking variable names;
- cartoonishly hostile prompts.

The vulnerability should emerge from ordinary data flow:

```text
untrusted data
    ↓
model context
    ↓
model decision/output
    ↓
privileged action
```

Positive examples are important. A safe AI change might:

- use a constrained classification interface;
- treat model output as a draft;
- require human approval;
- keep model output away from privileged side effects;
- use explicit data boundaries plus independent authorization.

Do not teach that a function called `sanitizePrompt()` makes a prompt safe.

## Language independence

The underlying scenarios are intentionally expressible in:

- TypeScript;
- Java;
- Python.

Avoid framework-specific tricks. Security concepts should survive translation between languages.

## Larger application knowledge

None of the primary 36 scenarios should require understanding an entire application.

Future advanced scenarios may be marked:

```text
requiresApplicationKnowledge = true
```

and can use larger applications such as OWASP Juice Shop. They should never become prerequisites for the basic booth interaction.

## AI comparison

The strongest AI-comparison scenarios are not necessarily those where AI misses a vulnerability.

Useful outcomes include:

- AI correctly finds a vulnerability;
- AI misses a vulnerability;
- AI finds a vulnerability but recommends an incomplete fix;
- AI overreacts to harmless code;
- AI approves a legitimate security improvement;
- AI focuses on security and misses a functional defect;
- AI identifies a pre-existing vulnerability but incorrectly concludes the current PR must be rejected;
- AI correctly distinguishes a security issue from the scope of the current change;
- AI identifies a prompt-injection risk but misses that model output has no authority;
- AI correctly identifies that model output crosses a privileged action boundary.

The most interesting long-term metric is therefore:

> **Did the reviewer make the correct ship/no-ship decision about this particular change?**

not merely:

> **Did the reviewer identify a vulnerability somewhere in the code?**

# Implementation Notes

## Attendee-visible fields

Keep the live UI extremely simple:

```text
Ticket
    ↓
Proposed change
    ↓
[ APPROVE ] [ DENY ]
```

Do not require the attendee to classify the reason.

## Internal scoring

Recommended fields:

```text
decision
decisionType
reasonType
difficulty
securityConcept
judgmentType
defensibleAlternatives
```

Judgment scenarios can either:

1. be excluded from the primary numerical score; or
2. receive a separate “review judgment” score.

Do not silently treat a defensible alternative as simply wrong.

## Randomization

Avoid serving closely related scenario families consecutively.

For example, do not intentionally serve:

```text
AI-01 → AI-02
```

or:

```text
SQL-01 → SQL-02
```

because attendees may learn the intended answer from the previous scenario rather than reviewing the current one.

Likewise, safe/unsafe variants should be treated as correlated samples by the randomizer.

## Theme application

Apply Spaceways theming only after the neutral scenario is finalized.

The theme may change:

- ticket title;
- nouns;
- names;
- sample values;
- surrounding narrative.

The theme must not change:

- security property;
- functional requirement;
- correct decision;
- difficulty;
- required reasoning.
